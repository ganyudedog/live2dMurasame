# 日志系统重构方案

## 1. 文档目的

本文档定义当前项目 renderer 侧日志系统的重构方案，也记录已经落地的核心实现，供后续迁移和审查。

本方案只涉及前端和共享层的日志架构，暂不修改 Electron 侧日志链路，也不引入完整的 OpenTelemetry 或其他重量级日志框架。

当前已落地：`ContextRegistry`、`TraceScope`、`end/fail` 两个输出出口、递归序列化和脱敏、源文件位置采集、全局异常入口，以及 Live2D 布局缩放、配置刷新、AI 对话、TTS、ASR 和 LiveKit 回环链路的迁移。AI/LiveKit 相关代码已经直接替换为 DI 注入的 `LogService` 与 `LiveKitService`，不再通过旧日志兼容入口。

目标是解决以下问题：

- 当前日志字段多但缺少业务含义，无法快速还原操作链路。
- 高频日志直接输出，导致控制台和 AI 分析上下文被大量重复数据占用。
- 全局异常目前只记录简单字符串，丢失 stack、cause、源文件和前置操作。
- Service、UI 和日志输出之间缺少清晰边界。
- 业务代码无法说明某个关联参数从什么值变化到什么值，以及变化后应该产生什么行为。

## 2. 总体原则

### 2.1 LogService 是唯一输出边界

所有日志必须通过 DI 注入的 LogService 输出。业务代码、UI 组件和状态模块不得直接调用 `console.log`、`console.warn` 或 `console.error`。

`console.*` 只允许存在于 LogService 的输出 Sink 内部。未来如果增加文件、远程或 Electron 镜像输出，也只能作为 LogService 的 Sink，不允许业务代码直接依赖这些目标。

### 2.2 记录和输出分离

日志事件先进入结构化 trace，由 LogService 统一序列化和决定是否输出：

```text
业务方法
  -> 变化检测器 / 副作用 / 监听器
  -> ContextRegistry 注册对象
  -> TraceScope 记录结构化数据
  -> LogService 序列化、脱敏
  -> ConsoleSink 或其他输出目标
```

正常模式和调试模式都只通过 `end()`、`fail()` 输出。普通事件只保存在当前 trace 中；调试模式的区别是允许观察更多中间数据，但这些数据仍然要等到两个终结出口之一才写入控制台。

### 2.3 业务层判断异常

LogService 不负责猜测某个值是否异常，也不负责对所有事件做语义去重、节流或合并。

参数变化是否符合预期，由具体 Service 的方法、监听器或副作用判断。例如 Live2D 缩放链路应由 `Live2dLayoutService` 判断 revision、比例、边界和窗口同步结果是否符合约束。

### 2.4 不使用全局可变 currentContext

浏览器中可能同时存在多个 Promise、事件回调和异步操作。单一的全局当前上下文会导致不同链路相互覆盖。

ContextRegistry 维护注册关系和 trace 索引，具体 Service 持有自己的注册对象或 TraceScope。异步操作通过句柄关联 trace，不通过全局变量推断当前链路。

### 2.5 结构化数据优先

每个关键事件都应包含具体数据，而不是只有一句描述。对于变化类事件，至少记录：

- `previous`：变化前的快照。
- `next`：变化后的快照。
- `delta`：可计算的变化量。
- `expected`：业务规则期望的结果。
- `actual`：实际结果。
- `reason`：触发该操作或判定的原因。
- `behavior`：该变化预期影响的后续行为。

业务代码不应把完整 Service、完整配置对象、大型模型对象或 DOM 对象放入日志数据中。

## 3. 模块职责

日志模块内部建议划分为以下职责，但对外仍由一个 DI 注入的 LogService 统一提供入口：

| 模块 | 职责 |
| --- | --- |
| `ContextRegistry` | 注册 Service 与关联参数，维护注册对象和 trace 关系 |
| `TraceScope` | 表示一次具体操作，保存步骤、参数变化和最终状态 |
| `SourceResolver` | 捕获并解析文件、行号、列号和函数名 |
| `Serializer` | 递归序列化、脱敏、循环引用处理和大小限制 |
| `ErrorCapture` | 统一处理业务错误、全局错误和 Promise 拒绝 |
| `ConsoleSink` | 输出人可读的摘要、分组详情和数据表 |
| `MirrorSink` | 暂不启用；Electron 侧日志重构完成后再作为独立输出目标评估 |

当前阶段不加入 `RateLimiter`、语义去重器或高频事件合并器。可以保留 trace 的事件容量和生命周期限制，但只用于防止内存无限增长，不改变事件内容。业务链路中的高频变化由具体方法、监听器或副作用检测，不由日志层吞掉。

## 4. ContextRegistry

### 4.1 注册方式

ContextRegistry 对外开放两个主要参数：

1. 对应的 Service 标识。
2. 与该 Service 关联的参数描述对象。

示例：

```ts
const context = logService.contextRegistry.register(
  'Live2dLayoutService',
  {
    relation: 'scale',
    params: {
      modelId,
      revision,
      scale,
    },
    behavior: 'scale 变化后重新计算布局并同步窗口尺寸',
  },
)
```

第一个参数使用稳定的 Service 名称，不直接保存 Service 实例，避免循环引用、意外序列化和生命周期泄漏。

第二个参数不是任意对象的原样引用，而是关联参数的有限快照和行为描述。它需要能够被 LogService 序列化。

### 4.2 注册对象

`register()` 返回一个注册对象。该对象不直接向控制台输出内容，而是提供与当前关联关系绑定的操作入口：

```ts
const trace = context.beginTrace('scale.apply')

trace.record('scale.changed', {
  previous: {
    value: previousScale,
    revision: previousRevision,
  },
  next: {
    value: nextScale,
    revision: nextRevision,
  },
  delta: nextScale - previousScale,
  behavior: '重新计算模型布局并同步窗口尺寸',
})

trace.record('layout.calculated', {
  bounds,
  width,
  height,
})

trace.fail('scale invariant violated', {
  expected,
  actual,
  reason,
})

trace.end()
```

建议注册对象包含以下能力：

```ts
type ContextRegistration = {
  beginTrace(operation: string, data?: Record<string, unknown>): TraceScope
  snapshot(): ContextSnapshot
  update(params: Record<string, unknown>): void
  dispose(): void
}
```

`update()` 只更新关联参数快照，不自动判断变化是否正确，也不自动输出日志。判断逻辑必须由所属 Service 或其监听器执行。

### 4.3 注册对象生命周期

- Service 初始化或某个业务关系建立时注册。
- 一次操作开始时调用 `beginTrace()`。
- 操作步骤通过 `record()` 添加到 trace。
- 出现异常时调用 `fail()`。
- 操作成功时调用 `end()`。
- Service 销毁、模型切换或关联关系失效时调用 `dispose()`。

注册对象必须具有明确的释放路径，避免模型反复切换时保留旧的上下文和闭包。

## 5. TraceScope

### 5.1 Trace 的定位

Trace 表示一个有限生命周期的业务操作，而不是整个应用的永久日志流。

建议的 trace 分组包括：

- `app.bootstrap`
- `config.refresh`
- `state.sync`
- `live2d.model-load`
- `live2d.scale`
- `ai.chat`
- `tts.playback`
- `asr.session`

Trace 名称表达业务链路，不以文件名作为主要分组。具体来源文件通过 `source` 字段记录。

### 5.2 Trace 数据模型

```ts
type TraceScope = {
  traceId: string
  service: string
  relation: string
  operation: string
  record(event: string, data: Record<string, unknown>): void
  fail(message: string, data?: Record<string, unknown>, cause?: unknown): TracedError
  end(data?: Record<string, unknown>): void
}
```

每个事件建议使用以下模型：

```ts
type LogEvent = {
  timestamp: number
  level: 'debug' | 'info' | 'warn' | 'error'
  service: string
  relation: string
  operation: string
  event: string
  traceId: string
  sequence: number
  data: Record<string, unknown>
  source?: SourceLocation
}
```

`sequence` 用来保证同一个 trace 内的步骤顺序，不依赖日志到达控制台的时间顺序。

### 5.3 Trace 状态

Trace 需要有明确状态：

```text
active -> completed
active -> failed
active -> expired
```

错误 trace 在输出后保留一段时间用于调试，但不能无限保留。建议先采用有限数量和 TTL，具体数值在实现和性能测试后确定。

## 6. 业务层变化检测

高频变化的处理方式是：业务层持续观察，只有不符合规则时才调用 LogService。

以 Live2D 缩放为例：

```text
收到新的 scale
  -> 保存 previous 和 next
  -> 检查 revision 是否单调递增
  -> 检查模型宽高比例是否符合预期
  -> 检查布局结果是否符合 scale 推导
  -> 检查窗口同步是否已经触发
  -> 正常：更新状态，不输出
  -> 异常：trace.fail()，输出完整链路
```

业务检测器需要明确描述规则，而不是只记录“发生了变化”。例如：

```ts
const expected = {
  revision: previous.revision + 1,
  widthRatio: next.scale / previous.scale,
  heightRatio: next.scale / previous.scale,
  windowUpdate: true,
}

const actual = {
  revision: next.revision,
  widthRatio: next.width / previous.width,
  heightRatio: next.height / previous.height,
  windowUpdate: didWindowUpdate,
}
```

当检测失败时，错误数据必须同时包含 `expected` 和 `actual`，这样无需重新运行程序即可判断问题发生在哪个环节。

LogService 不负责执行这些业务规则。它只保存检测结果并负责输出。

## 7. 输出策略

### 7.1 正常模式

正常模式下：

- `TraceScope.record()` 只把中间步骤和具体数据写入当前 trace，不直接输出。
- `TraceScope.end()` 是成功操作的正式输出出口，输出成功摘要、调用 `end()` 的源文件行号和完整 trace 数据。
- `TraceScope.fail()` 是异常操作的正式输出出口，输出错误摘要、调用 `fail()` 的源文件行号、错误数据、cause、stack 和完整 trace 数据。
- 没有关联 trace 的异常自动创建 `renderer.unhandled` trace。

`end()` 和 `fail()` 是唯一的 trace 输出出口。这样正常运行和 scale 拖动不会把重复的中间值写入控制台，同时一个看似成功但实际存在问题的操作仍然能够留下完整现场。

### 7.2 调试模式

调试模式开启后：

- `TraceScope.record()` 仍然只记录，不输出中间事件。
- 调用 `TraceScope.end()` 时输出成功 trace 和所有中间事件。
- 调用 `TraceScope.fail()` 时输出失败 trace、完整错误现场和所有中间事件。
- `end()` 和 `fail()` 输出的每个事件都包含业务数据和 source。
- 复杂数据使用折叠组展示，关键数组和对象可以使用 `console.table` 展示。

调试模式的开关由 LogService 管理，不由各个 Service 自己判断。这样切换调试模式不会改变业务逻辑。

### 7.3 错误模式

调用 `TraceScope.fail()` 或 `LogService.captureException()` 时，LogService 输出以下内容：

1. 错误摘要和失败出口。
2. `traceId`、Service、relation 和 operation。
3. 错误事件的具体数据。
4. Trace 中的所有前置事件。
5. 每个事件的 source。
6. 当前上下文快照。
7. `cause`、错误堆栈和全局错误来源。
8. Trace 的最终状态。

成功调用 `TraceScope.end()` 时也输出相同结构，但状态为 `completed`，并且必须明确标记 `end()` 调用位置。`end()` 用于定位“流程表面成功，但后续结果仍然异常”的问题；`fail()` 用于明确的异常兜底。

### 7.4 AI 与 LiveKit 回环

AI、TTS、ASR 和 LiveKit 不再调用兼容日志函数。它们通过 DI 获取 `LogService`，由业务 Service 创建上下文并持有 trace：

```text
AiService
  -> Stage2 trace
  -> TTS runtime trace
  -> LiveKitService
  -> 前端 publish event
  -> 后端 LiveKit event
  -> requestId/sessionId 关联
  -> 同一 trace record
  -> end() 或 fail()
```

LiveKit 入站事件至少保留 `topic`、`type`、`sessionId`、`requestId` 和后端 `payload`。HTTP 会话、房间连接、事件发布、事件接收和回环关联全部归属于同一个 `LiveKitService`，不再创建独立的 realtime service。`tts.speak` 使用 `requestId` 建立请求 trace，后端返回 `tts.error` 时调用 `fail()`，返回 `tts.finished` 或 `tts.canceled` 时调用 `end()`。因此失败输出包含发送参数、发布结果、后端回环事件和终态数据，而不会依赖另一套独立的日志格式。

示例：

```text
ERROR [live2d.scale] scale 变化违反布局约束
trace=scale-8f31
service=Live2dLayoutService
relation=scale
operation=scale.apply
source=src/app/live2d/Live2dLayoutService.ts:241:17

data:
{
  "parameter": "scale",
  "previous": {
    "value": 1.24,
    "revision": 183,
    "modelWidth": 840,
    "modelHeight": 1180
  },
  "next": {
    "value": 1.31,
    "revision": 184,
    "modelWidth": 886,
    "modelHeight": 1247
  },
  "delta": 0.07,
  "expected": {
    "revision": 184,
    "widthRatio": 1.056,
    "heightRatio": 1.057,
    "windowUpdate": true
  },
  "actual": {
    "widthRatio": 1.055,
    "heightRatio": 1.083,
    "windowUpdate": false
  },
  "behavior": "scale 变化后重新计算布局并同步窗口尺寸"
}
```

展开 trace 后，还应看到类似以下步骤：

```text
00.000  scale.changed
       data={ previous: ..., next: ..., delta: 0.07 }
       source=Live2dLayoutService.ts:198

00.421  layout.calculated
       data={ bounds: ..., width: 886, height: 1247 }
       source=Live2dLayoutService.ts:216

00.936  window.sync.completed
       data={ requested: ..., actual: ... }
       source=WindowService.ts:143

01.204  scale.invariant.failed
       data={ expected: ..., actual: ... }
       source=Live2dLayoutService.ts:241
```

## 8. 源文件和行号

### 8.1 Vite 开发模式

LogService 在记录事件时捕获调用栈，跳过日志模块内部栈帧，解析第一个业务栈帧：

```text
http://localhost:5173/src/app/live2d/Live2dLayoutService.ts:241:17
```

解析后保存为：

```ts
type SourceLocation = {
  moduleUrl?: string
  file?: string
  line?: number
  column?: number
  functionName?: string
}
```

`import.meta.url` 可以补充当前模块 URL，但不能单独提供调用方行号。调用方位置主要来自 `Error.stack`，Vite 的开发 sourcemap 用于映射回 `.ts/.tsx` 文件。

### 8.2 性能策略

源位置捕获需要读取 stack，存在额外成本。建议：

- 业务检测器产生的关键事件记录 source。
- 普通内部状态更新不进入 LogService，因此不会频繁采集 stack。
- 错误事件始终采集完整 source 和 stack。
- 正常模式保存紧凑的文件、行号和列号，不保存完整 stack。
- 未来如果需要绝对稳定的源位置，再增加仅开发模式启用的 Vite transform 注入文件和行号。

## 9. LogService 序列化

所有事件在 LogService 内部统一序列化，调用方只提交结构化数据。

序列化器需要处理：

- 递归对象。
- 循环引用。
- `Error`、`Date`、`Map`、`Set` 等特殊类型。
- 最大递归深度。
- 最大对象字段数。
- 最大数组长度。
- 最大字符串长度。
- 敏感字段脱敏。
- 不可序列化值的安全降级。

敏感字段至少包括：

```text
token
accessToken
apiKey
secret
password
authorization
cookie
```

脱敏应递归执行，不能只处理第一层。对循环对象、过大的数组或未知类实例，应输出有限的类型和摘要，而不是抛出新的序列化错误。

## 10. 错误上下文和全局兜底

业务错误统一通过带 trace 的错误对象传递：

```ts
class TracedError extends Error {
  traceId: string
  contextSnapshot: unknown
  source?: SourceLocation
  cause?: unknown
}
```

建议提供：

```ts
trace.fail(message, data, cause): TracedError
logService.captureException(error, options): void
```

全局入口统一调用 `captureException()`：

- `window.error`。
- `window.unhandledrejection`。
- React Error Boundary。
- 关键异步任务的统一错误出口。

如果异常已经携带 `traceId`，LogService 找回已有 trace 并展开；如果是普通异常，则创建 `renderer.unhandled` trace。

全局异常不应只记录 `String(message)`，至少需要包含：

- message。
- name。
- stack。
- cause。
- source。
- traceId。
- 当前上下文快照。
- 异常来源。

## 11. 与现有 DI 和分层架构的关系

LogService 继续通过现有 DI Token 注入，Service 不直接创建日志实例。

推荐使用关系：

```text
TOKENS.log
  -> LogService
      -> ContextRegistry
      -> TraceStore
      -> Serializer
      -> ErrorCapture
      -> ConsoleSink
```

Service 只依赖 LogService 的接口或受限的 scoped logger，不依赖 Console、Vite API、Electron API 或具体输出格式。

UI 只触发用户操作和状态变化，不负责决定日志字段和错误输出格式。业务 Service 负责定义关联参数和规则，LogService 负责统一记录和输出。

如果需要避免业务 Service 自己拼接 namespace，可以由 LogService 提供：

```ts
const logger = logService.scope('live2d.scale')
```

但 `scope()` 只是绑定 Service/业务分组的轻量门面，实际记录、序列化和输出仍然回到 LogService。

## 12. 迁移步骤

### 阶段一：定义契约

定义以下类型和接口：

- `ContextRegistration`。
- `ContextSnapshot`。
- `TraceScope`。
- `LogEvent`。
- `SourceLocation`。
- `TracedError`。
- `LogService.captureException()`。

现有 `debug/info/warn/error` 暂时保留，作为兼容层进入新的记录模型。

### 阶段二：实现 LogService 内核

实现：

- ContextRegistry。
- TraceStore。
- SourceResolver。
- Serializer。
- 调试开关。
- 错误时展开完整 trace。
- 全局错误入口。

此阶段不修改 Electron 侧，也不从 renderer LogService 向 Electron 镜像日志。

### 阶段三：迁移代表性链路

优先迁移：

1. `Live2dLayoutService` 的 scale 链路。
2. Live2D 模型加载链路。
3. 配置刷新链路。

迁移时删除逐帧布局、原始状态总线对象和完整配置对象输出，改为记录参数快照和业务检测结果。

### 阶段四：全面审计

对剩余日志逐条归类：

- 业务步骤记录。
- 调试事件。
- 业务约束错误。
- 全局异常。
- 无法帮助定位问题的日志，直接删除。

最后禁止 renderer 业务代码直接调用 `console.*`，并更新日志文档和开发约定。

## 13. 验收标准

- 正常 scale 拖动不向控制台输出高频日志。
- 调试模式下可以看到每个关键步骤的具体数据。
- 任意错误都能输出完整 trace，而不是只输出错误字符串。
- 错误数据同时包含 previous、next、expected 和 actual。
- 每个关键事件都能定位到业务文件和行号。
- 并发的两个 trace 不会互相覆盖或串线。
- 全局未捕获异常能够关联已有 trace。
- 序列化不会因为循环对象、Error 或特殊类型再次抛错。
- 敏感字段不会出现在输出中。
- Trace 有明确的数量和生命周期上限。
- UI、Service 和输出 Sink 之间没有直接耦合。
- Electron 镜像暂不启用，后续 Electron 日志重构完成后再单独接入 Sink。

## 14. 暂不纳入的内容

- Electron 侧日志系统重构。
- 完整 OpenTelemetry 接入。
- 自动推断所有业务参数变化。
- LogService 内部的去重、节流和语义合并。
- 生产环境源码映射和远程日志平台接入。

这些内容可以在前端日志链路稳定后单独评估。
