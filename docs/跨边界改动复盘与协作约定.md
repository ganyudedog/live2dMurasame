# 跨边界改动复盘与协作约定

这份文档用于开发、审查和验收涉及插件、主进程、渲染进程、外部消息渠道、文件上传和模型评估的改动。它把本次 Feishu、NapCat、benchmark、Cubism 和图片上传改动中出现的共性问题固化为执行规则。

## 共性偏差

### 先设计了抽象，再确认数据归属

主进程拥有长连接、命令目录、配置和发件箱。渲染进程拥有界面、输入采集和对话编排。外部渠道插件拥有渠道协议、角色判断和渠道内命令选择。数据产生侧应保存数据并执行动作，另一侧沿已有出口提交请求或接收结果。

出现以下信号时，应停止新增中间层并重新定位数据拥有者。

- 窗口需要把函数登记回主进程
- 内核需要知道某个具体插件的角色规则
- 同一份凭据同时存在于 CLI、设置页和长连接实例
- 为了接入渠道新增一条只转发消息的后端 bridge
- 一个通用接口开始写死某个命令名或插件名

### 把“已接收”当成“已完成”

外部消息处理至少要区分以下状态。

1. 收到并绑定了消息
2. 已提交给对话编排
3. 回复正文已经生成
4. 回复已经进入发件箱
5. 渠道确认回复已发出
6. 失败后可以重试，或者已经写回可见的失败说明

去重标记、原文清理和提醒完成状态只能绑定到项目定义的完成边界。模型失败、取消、空回复、发送未接受和连接暂时失败都不能清掉仍需处理的消息。每个渠道都要有覆盖延迟回执、重复回执、发送失败和重连的测试。

### 把协议适配责任推给模型或调用者

读取接口返回的数据形状和更新接口接受的数据形状通常不同。插件 CLI 应在边界内完成适配。

以云文档为例，`read` 返回块列表，`update` 应接收读取结果中的 `block_id` 和可修改内容，由 CLI 组装 `update_text_elements` 等飞书 PATCH 正文。调用者只描述修改意图，不承担飞书 API 的请求形状转换。

### 用具体实现名代替通用契约

日志、请求持久化和 benchmark 处理必须依据请求契约判断字段。`codex.task` 只能是一个命令名称，不能成为所有可记录请求的分支条件。需要排除图片等大字段时，应定义通用的可序列化策略或按请求协议判断，而不是把某个命令名写进核心代码。

同样，存储 key 的命名空间、临时数据的生命周期和持久化范围必须由存储接口定义。业务调用方不应通过字符串前缀猜测存储实现。

### 把接线回归当成模型评估

Jaeger 中的边界名、span 成功状态和应用观察值可以用于接线回归。模型行为评估需要同一次真实调用的模型输入、工具调用参数、工具结果、最终回复和验收规则。

`eval/draft.ts` 应从完整 trace 生成可重放案例。`eval/cases/` 中的人工案例用于固定回归。两者应保持入口和数据责任分开。Promptfoo 的 provider 应返回完整的案例观察值，`accept()` 决定是否通过，断言需要能暴露输入、工具上下文、回复和失败原因。

日志属性策略需要为 benchmark 原始数据保留明确出口。截断和敏感字段过滤必须在设计文档中说明，不能让案例生成依赖一次偶然写在过滤器之后的字段。

### 用 mock 绕过正在修复的边界

测试替换了出问题的启动、发送、文件转换或 DOM 层时，只能证明编排逻辑。涉及边界修复时，至少补一条到真实边界的测试，范围可以停在握手、请求体生成、发件箱接收或一次真实模型调用。

当前 Vitest 默认环境是 Node。之前的 DOM 测试通过 stub `window`、`document` 和 `createRoot` 完成。图片上传测试需要真实挂载 React、`File`、`FileReader`、文件选择和粘贴事件，因此在 `FloatingComposer.images.test.tsx` 内单独启用 `jsdom`。新增测试环境时，应说明它模拟了哪一个真实边界。

## 描述不足造成的误解

下面的表述在本次对话中曾引起实现方向变化。后续需求应直接补充右侧信息。

| 容易产生歧义的表述 | 应明确的含义 |
| --- | --- |
| “飞书自带鉴权” | 渠道已经证明消息来源，但插件仍需要根据 `isOwner` 决定是否展示和执行额外命令。鉴权来源、角色映射和命令授权分别写清。 |
| “只有 owner 才能用插件” | 说明是只有 owner 能用插件额外命令，还是只有 owner 能进行任何插件对话。普通成员能否聊天、能否使用内核命令、developer 能否使用渠道能力都要列出。 |
| “发送通了”或“回执成功” | 说明是连接建立、请求被接受、消息进入发件箱、渠道确认发送，还是用户已经看到回复。每种状态对应不同的完成语义。 |
| “先做真实验收” | 说明需要验证哪条外部链路、允许验证到哪一步、用户需要提供哪些配置、哪些能力暂时跳过。 |
| “云文档可以编辑” | 说明是读取块、更新已有块、追加内容，还是新建文档，并提供真实 API 接受的请求形状和验收结果。 |
| “从 Jaeger 提取 benchmark” | 说明是提取应用接线回归，还是保留模型输入、工具结果和回复来重放一次模型行为。 |
| “加临时存储” | 说明生命周期、是否落盘、谁负责清理、是否允许跨进程读取，以及它和普通插件存储的边界。 |
| “参考 Codex 的图片上传” | 说明需要复制粘贴、文件选择、预览、删除、大小限制、请求编码和失败反馈中的哪些行为。 |
| “旧数据可以不保留” | 说明适用哪些数据。插件目录、主人授权、连接配置、未发送提醒、去重记录和 benchmark 案例需要分别确认。 |

用户补充了新的边界后，后续实现以最新明确规则为准，同时保留旧规则中仍然有效的部分。出现“通了”“可以”“先不管”等短句时，只把它当作当前阶段状态，不把它自动扩展成永久接口契约。

## 权限与角色约定

渠道鉴权和应用内角色判断分成两层。

- 飞书、NapCat 等渠道负责证明消息来自哪个账号或会话
- 插件根据渠道身份和 `isOwner` 决定是否提供插件额外能力
- 普通成员可以进行普通对话，并使用允许所有对话使用的内核命令
- developer 身份可以使用渠道插件允许的能力
- 只有 owner 可以使用需要主人权限的插件额外命令
- 内核只接收调用上下文和必要的身份信息，不保存 Feishu 或 NapCat 的角色规则

除非出现明确的跨插件安全需求，不在内核增加针对单个插件的 `turnPolicies`、`commandFilters` 或 `memberCommands`。插件应在登记命令、生成命令目录或调用前完成自己的能力筛选，内核负责通用参数校验、来源绑定和执行边界。

## 开始改动前的最小契约

每个跨边界需求先写下以下内容，随后再决定文件位置。

- 数据由哪一侧产生，哪一侧保存
- 请求从哪里发起，执行函数由谁拥有
- 用户看到的完成结果是什么
- 哪个回执或状态才算完成
- 失败、取消、空结果和重试如何处理
- 调用者身份由谁证明，owner 规则由谁解释
- 真实 API 接受的请求体和读取接口返回的形状
- 测试需要停在哪个边界，证据来自日志、回执、发件箱还是模型响应
- 是否涉及旧插件 ID、旧配置、旧提醒或旧去重状态
- 是否需要重启、重新扫描插件或重新建立长连接

如果其中一项会改变权限、数据丢失、消息可见性或外部副作用，先补充契约再写实现。只影响局部展示的需求可以直接沿已有入口修改。

## 交付前检查

- 检查实际仓库根目录、当前分支、工作树和最终 diff
- 检查数据拥有侧是否保存并执行了新增状态
- 检查窗口是否只通过 IPC 提交请求和接收状态
- 检查插件命令是否从主进程命令目录进入
- 检查成功语义是否对应用户可观察的最后一步
- 检查失败消息是否仍可重试或可见
- 检查真实请求体、回执和重连路径
- 检查新增测试是否验证了目标边界
- 对未完成的外部验收明确标注证据范围，不用中间状态替代最终结果
