# 桌宠窗口几何与布局重构方案

## 背景

当前桌宠窗口在手势拖动时存在明显抖动、串轴滑动、停住后继续偏移的问题。问题不是单一公式错误，而是当前窗口几何、渲染布局、交互布局三类状态形成了反馈环。

当前链路大致如下：

1. 主进程修改窗口位置或尺寸。
2. 主进程通过 IPC 将窗口事实回流给 renderer。
3. renderer 中多个 hook 基于最新 bounds 分别重算模型布局、气泡布局、上下文区布局、鼠标穿透状态。
4. 其中部分重算又继续发出新的窗口意图，或更新后续几何计算输入。
5. 主进程再次修改窗口几何并再次回流。

这条链在拖动过程中不断重复，直到系统收敛到某个稳定态。用户看到的就是抖动、左右晃动、纵向下滑、停住后仍继续漂移。

本方案的目标不是继续局部冻结，而是从架构上拆掉几何反馈环。

## 当前核心问题

### 1. 窗口几何没有唯一作者

主进程虽然是实际窗口几何的执行者，但 renderer 中多条链路仍然持有窗口几何治理权，例如：

1. 中心线纠偏会发送 position intent。
2. 气泡布局会根据宽度需求触发 size intent。
3. bounds 回流会再次触发布局与交互区重算。

结果是一次拖动并不是纯粹的窗口平移，而会被 renderer 解释为一次需要重新求解最终几何形态的事件。

### 2. 显示布局和窗口治理混在同一层

当前气泡布局、上下文区布局、拖拽手柄布局、baseline 维护、窗口宽度策略并没有严格分层。特别是气泡布局函数既负责计算视觉位置，又具备窗口宽度治理能力，导致显示计算本身变成了窗口控制链的一部分。

### 3. baseline 存在多作者

centerBaseline 目前由多个模块写入，包括：

1. 启动初始化。
2. 布局初始化。
3. cursor 轮询。
4. 气泡重置。
5. resize orchestrator。

这意味着 baseline 既是输入、也是中间态、也是纠偏结果，语义不稳定。

### 4. 交互重算会放大主闭环

上下文区命中、鼠标穿透、cursor 轮询、drag handle 位置更新并不一定直接修改窗口几何，但它们会显著提升拖动期间的重算频率，成为主闭环的放大器。

## 重构目标

本次重构目标如下：

1. 将窗口几何、渲染布局、交互布局彻底分层。
2. renderer 内部仅保留一个统一入口负责布局总计算。
3. renderer 到主进程的窗口相关通信收敛为唯一出口。
4. 保留现有 drag 手势和现有 IPC 协议，不额外引入新的分裂式通信模型。
5. 将拖动过程变成受状态机约束的 session，而不是普通 pointermove 的副产物。
6. 使布局计算尽可能纯函数化，降低 hook 间的耦合。

## 总体设计原则

### 原则 1：主进程是窗口几何唯一作者

窗口的 x、y、width、height 只能由主进程真正写入。renderer 不能再由多个局部模块分别决定是否修改窗口几何。

### 原则 2：renderer 内部布局优先使用窗口内部坐标系

模型、气泡、上下文区、拖拽手柄等内部布局应尽量依赖窗口内部宽高、模型 bounds、pointer 相对位置、布局参数，而不是直接依赖窗口 screen x、screen y 作为常规布局输入。

### 原则 3：布局求解与副作用提交分离

所有布局模块先输出纯计算结果，再由统一入口决定是否提交给：

1. React state
2. canvas model position
3. 主进程窗口命令
4. 鼠标穿透桥接

### 原则 4：拖动是一个 session，而不是普通 move

拖动开始后，系统应进入 drag session。dragging 阶段下，窗口平移必须视为主进程真值传播，不再触发 renderer 内的二次窗口治理。

## 当前实现进度

以下内容用于记录当前代码与本文档目标之间的对齐情况，避免“文档已设计完成，但实现状态不透明”。

### 已完成的部分

1. 已建立 GeometryRuntime，window fact 与 window intent ack 已统一消费。
2. 已建立 WindowCommandGateway，renderer 侧发送 pet:windowIntent 已基本收口到单一出口。
3. 已建立 BaselineController，baseline 不再由 bubble reset、cursor tracking、bootstrap 等路径直接散写。
4. 已拆出 ModelLayoutSolver、BubbleWindowRequirement solver、ContextZoneLayoutSolver、ContextZoneActivitySolver、InteractivitySolver。
5. 已建立 DragSessionController，dragging、pending-drag、settling 等状态已进入一级运行时状态机。
6. PetCanvas 已明显向装配层演进，局部布局公式和拖动态门控已开始迁入 runtime/solver/policy 层。
7. pet:windowDrag 已调整为“主进程拥有 drag session”的语义：renderer 只发送 start/end，拖动持续位移完全由主进程在 session 内主动轮询全局鼠标屏幕坐标并驱动窗口位置。
8. drag session 已补上双端收束机制：结束真值不再依赖“停止移动”或最大持续时间，而是只依赖 pointerup/cancel/blur 与 Windows 原生鼠标释放消息；主进程确认释放后会反向同步 renderer 结束本地 session，renderer 会在 stable 边界重放一次 bubble 和交互布局，使拖动期延后的窗口策略只在稳定态恢复。

### 尚未彻底完成的部分

1. useBubblePositionEngine 仍同时承担 bubble 显示测量与 DOM 布局提交；虽然它已经改为在 pending-drag、dragging、settling 期间只保留宽度需求计算、不直接扩窗，但 bubble 宽度需求仍需继续收束到统一 orchestrator，而不是停留在装配层调度。
2. usePetResizeOrchestrator 虽然已有部分策略外提到 WindowPolicyEngine，但它仍保留 resize/align 的主要窗口治理编排职责。
3. GeometryRuntime 目前仍更偏向“统一输入入口”，尚未完全成为输出 LayoutSnapshot 与 WindowCommand 的唯一 orchestrator。
4. LayoutCommitter 尚未独立成模块，当前 model、bubble、context zone、interactivity 的提交仍分散在 PetCanvas 和若干 committer hook 内。

### 当前阶段判断

当前代码已经完成“单入口/单出口/单 baseline 作者/单 drag session 状态机 + 拖动期窗口策略门控”的主干搭建，但尚未达到本文档中“窗口布局、气泡布局、baseline 布局完全解耦且由 orchestrator 统一编排”的最终状态。

## 目标架构

建议将 renderer 侧重构为五层。

### 一、输入层 Input Layer

职责：接收事实，不做布局治理。

输入统一汇聚为一个运行态快照 GeometryInputSnapshot，包含：

1. windowFacts
	- bounds
	- lastAppliedIntentId
	- ack
2. dragSession
	- state
	- pointer start
	- pointer current
3. pointerFacts
	- pointerX
	- pointerY
	- screen point
4. modelFacts
	- model bounds
	- visible frame
	- base frame
	- scale
5. uiFacts
	- motionText
	- motionSound
	- ignoreMouse
	- current config snapshot

当前分散在以下模块的事实输入，最终都应汇聚到统一输入层：

1. src/renderer/components/pet/hooks/usePetModel.ts
2. src/renderer/components/pet/hooks/usePointerTapHandler.ts
3. src/renderer/components/pet/hooks/useCursorTracking.ts
4. src/renderer/components/pet/hooks/useMousePassthrough.ts
5. src/renderer/components/pet/hooks/usePetCanvasBootstrap.ts

### 二、纯布局层 Pure Solver Layer

这一层只做纯计算，不直接发 IPC，不直接 setState，不直接调用 WindowAPI。

#### 1. ModelLayoutSolver

输入：

1. window inner size
2. model bounds
3. scale
4. baseline policy
5. anchor policy

输出：

1. model positionX
2. model positionY
3. model scale
4. pivotX
5. pivotY

职责：完全替代当前散落在 PetCanvas applyLayout 中的模型摆位逻辑。

#### 2. BubbleLayoutSolver

输入：

1. model visible/base frame
2. bubble text state
3. bubble settings
4. container size
5. scale

输出：

1. bubble visible
2. bubble side
3. bubble left/top
4. bubble tailY
5. symmetric zone metrics
6. requiredWindowWidth

注意：

1. 只计算 requiredWindowWidth。
2. 不允许直接决定是否扩窗。
3. 不允许直接写 baseline。

#### 3. ContextZoneLayoutSolver

输入：

1. model visible bounds
2. container size
3. pointer relative position
4. layout config

输出：

1. context zone alignment
2. context zone rect
3. context zone absolute rect for hit test

职责：只负责上下文区几何。

#### 4. InteractivitySolver

输入：

1. pointer facts
2. model hit result
3. bubble rect
4. context zone rect
5. drag handle rect
6. drag session state
7. ignoreMouse

输出：

1. pointerInsideModel
2. pointerInsideBubble
3. pointerInsideContextZone
4. pointerInsideHandle
5. shouldCapture
6. shouldPassthrough

职责：只做交互态判定，不直接调用 setMousePassthrough。

#### 5. BaselineController

这是一个独立控制器，而不是普通 solver。

职责：维护单一语义的 baseline 状态。

baseline 在重构后只允许两类更新：

1. 初始化建立。
2. 明确的 resize 稳定提交后更新。

明确禁止以下路径直接写 baseline：

1. cursor tracking 轮询。
2. bubble clear/reset。
3. 普通 move-only bounds 回流。
4. 局部 hook 的布局补偿逻辑。

### 三、策略层 Policy Layer

这一层只负责决定是否需要窗口级命令，不直接通信。

#### WindowPolicyEngine

输入：

1. 当前 drag session state
2. latest window facts
3. ModelLayoutSolver 输出
4. BubbleLayoutSolver 输出
5. ContextZoneLayoutSolver 输出
6. BaselineController 状态

输出：

1. no-op
2. resize command
3. optional post-drag settle command

约束：

1. dragging 状态下禁止输出 position command。
2. dragging 状态下禁止输出 size command。
3. move-only bounds 回流不允许触发新的窗口治理。
4. 只有明确策略命中时，才允许输出一条窗口命令。

### 四、统一编排入口 Orchestrator Layer

这是本次重构的中心。

建议新增 GeometryRuntime 或 LayoutOrchestrator，作为 renderer 内部唯一的几何编排入口。

职责：

1. 统一收集 GeometryInputSnapshot。
2. 按固定顺序调用所有 solver/controller。
3. 生成一个 LayoutSnapshot。
4. 生成最多一个 WindowCommand。
5. 把 LayoutSnapshot 提交给 renderer 展示层。
6. 把 WindowCommand 交给唯一通信出口。

必须保证：

1. 一轮事实输入最多触发一次总求解。
2. 一轮总求解最多产生一次窗口命令。
3. 除 Orchestrator 外，不允许其他 hook 直接与主进程谈窗口几何。

### 五、单一提交出口 Commit Layer

#### 1. LayoutCommitter

职责：把 LayoutSnapshot 提交给本地 UI 和模型。

包括：

1. 设置 model position/scale/pivot。
2. 更新 bubble React state。
3. 更新 context zone React state。
4. 更新 drag handle state。
5. 更新 interactivity derived state。

#### 2. WindowCommandGateway

职责：renderer 到 main 的唯一窗口几何通信出口。

约束：

1. 只允许 Orchestrator 调用。
2. 继续复用现有 pet:windowIntent IPC。
3. 统一做 request coalescing。
4. 同类命令在同一帧只发送一次。

## 建议的状态机

继续复用当前 drag state 语义，但升级为一级运行时状态机。

建议状态如下：

1. idle
	- 正常稳定态。
	- 允许完整布局求解。
	- 允许窗口策略层输出少量命令。

2. pending-drag
	- pointer down 后、超过阈值前。
	- 允许点击判定。
	- 禁止窗口策略输出窗口命令。

3. dragging
	- 已确认拖动。
	- 主进程位置单写。
	- renderer 允许做本地显示求解。
	- 禁止输出 position/size 窗口命令。
	- move-only bounds 只作为事实更新，不触发窗口治理。

4. settling
	- 拖动结束，等待最终几何稳定。
	- 允许接收最终 bounds。
	- 不立刻恢复完整策略输出。

5. stable
	- 过渡完成。
	- 再次允许完整布局与窗口策略。

## IPC 约束

不新增新的窗口几何协议，继续复用当前已有 IPC。

### 保留的 IPC

1. pet:windowDrag
	- 用于拖动会话的 start、end。
	- 主进程在收到 start 后会进入 drag session，并以主进程侧鼠标屏幕坐标作为持续位移真值。
	- 当主进程通过原生消息确认拖动已经结束时，也会复用同一通道反向同步 end 给 renderer，用于收束本地 pointer/session 状态。
	- 明确禁止用“鼠标短时间未移动”推断拖动已结束，因为按住不动仍然属于 drag session 存续期。

2. pet:windowIntent
	- 用于统一窗口治理命令。
	- 只能由 WindowCommandGateway 发出。

3. pet:windowFact
	- 主进程回流窗口事实。
	- 只能由 Orchestrator 消费。

4. pet:windowIntentAck
	- 主进程返回窗口治理命令确认。
	- 只能由 Orchestrator 消费。

### 明确禁止

以下模块不允许再直接发送窗口命令：

1. BubbleLayoutSolver
2. ContextZoneLayoutSolver
3. InteractivitySolver
4. ModelLayoutSolver
5. cursor tracking
6. local effect hook

## LayoutSnapshot 设计

统一入口每次输出一个 LayoutSnapshot，建议结构如下：

```ts
interface LayoutSnapshot {
  revision: number;
  reason: 'bootstrap' | 'scale' | 'window-fact' | 'drag' | 'motion' | 'pointer' | 'settle';
  dragSession: {
	 state: 'idle' | 'pending-drag' | 'dragging' | 'settling' | 'stable';
  };
  window: {
	 bounds: { x: number; y: number; width: number; height: number } | null;
	 innerWidth: number;
	 innerHeight: number;
  };
  model: {
	 positionX: number;
	 positionY: number;
	 scale: number;
	 pivotX: number;
	 pivotY: number;
  };
  bubble: {
	 visible: boolean;
	 side: 'left' | 'right' | null;
	 left: number | null;
	 top: number | null;
	 tailY: number | null;
	 requiredWindowWidth: number | null;
  };
  contextZone: {
	 visible: boolean;
	 alignment: 'left' | 'right' | null;
	 left: number | null;
	 top: number | null;
	 width: number | null;
	 height: number | null;
  };
  interactivity: {
	 pointerInsideModel: boolean;
	 pointerInsideBubble: boolean;
	 pointerInsideContextZone: boolean;
	 pointerInsideHandle: boolean;
	 shouldCapture: boolean;
	 shouldPassthrough: boolean;
  };
}
```

## WindowCommand 设计

统一出口每次最多允许提交一条 WindowCommand。

```ts
type WindowCommand =
  | { type: 'none' }
  | {
		type: 'resize';
		width: number;
		height: number;
		preserveCenterLine?: boolean;
		source: 'bubble-policy' | 'scale-policy' | 'stable-settle';
	 };
```

本阶段不再允许 renderer 输出 position command。窗口位置只由拖动或主进程显式治理决定。

## 分阶段实施顺序

### 第一阶段：收权

目标：先建立单一入口和单一出口，哪怕内部计算逻辑仍复用旧代码。

步骤：

1. 新建 GeometryRuntime。
2. 将 windowFact 和 windowIntentAck 的消费统一汇总到 GeometryRuntime。
3. 禁止其他局部 hook 直接发 window intent。
4. 建立 WindowCommandGateway，成为唯一窗口命令出口。

完成标准：

1. renderer 侧窗口命令只有一个发送点。
2. windowFact 只有一个统一消费点。

### 第二阶段：拆 Bubble

目标：把气泡显示计算和窗口宽度治理分离。

步骤：

1. 从 useBubblePositionEngine 中抽出纯 BubbleLayoutSolver。
2. BubbleLayoutSolver 仅输出 requiredWindowWidth，不直接扩窗。
3. WindowPolicyEngine 决定是否在 stable 状态下发 resize command。

完成标准：

1. 气泡计算不再直接调用 applyWindowWidth。
2. 气泡显示链不具备窗口写权限。

### 第三阶段：拆 Baseline

目标：让 baseline 成为单作者状态。

步骤：

1. 新建 BaselineController。
2. 移除 cursor tracking、bubble reset、普通 bounds 回流对 baseline 的写入。
3. 仅保留初始化和 resize 稳定提交后的更新。

完成标准：

1. baseline 写入点收敛为一个控制器。

### 第四阶段：拆 Interactivity

目标：把上下文区布局、命中判定、穿透策略从局部 hook 分离出来。

步骤：

1. 抽出 ContextZoneLayoutSolver。
2. 抽出 InteractivitySolver。
3. useMousePassthrough 仅负责提交最终 interactivity output。
4. useCursorTracking 只保留 pointer facts 输入。

完成标准：

1. pointerInside 与 shouldPassthrough 不再由多个 hook 分散 recompute。

### 第五阶段：拖动状态机接管

目标：拖动时让系统进入真正的 drag session。

步骤：

1. dragging 状态下禁用 WindowPolicyEngine 输出窗口命令。
2. move-only bounds 回流仅更新 GeometryInputSnapshot，不触发窗口治理。
3. drag end 后进入 settling，再恢复稳定策略。

完成标准：

1. 拖动过程中 renderer 不再尝试纠偏窗口几何。
2. 拖动结束后只发生一次稳定态同步。

## 明确不再采用的做法

以下方案不作为最终架构方向：

1. 在识别拖动后动态切换 WebkitAppRegion: drag。
2. 继续在多个局部 hook 内分散发送 window intent。
3. 继续使用多个模块共同写 baseline。
4. 继续让 bubble 显示函数直接治理窗口宽度。
5. 继续把拖动看成普通 pointermove，而不是 drag session。

## 验收标准

当以下条件同时满足时，认为本次架构拆环成功：

1. 手势拖动模型时，窗口移动平滑，无明显抖动。
2. 横向拖动后停住，不再出现向下滑动。
3. 纵向拖动后停住，不再出现向右滑动。
4. 拖动期间 renderer 不再发 position/size 二次治理命令。
5. 气泡仍保留左右对称切换能力。
6. 上下文区、鼠标穿透、拖拽手柄仍可用。
7. 布局模块之间输入输出关系明确，可单独测试。
8. 现有 pet:windowDrag、pet:windowIntent、pet:windowFact、pet:windowIntentAck 仍然可复用。
