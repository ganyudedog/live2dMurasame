# 跨边界改动的验收约定

供开发和审查使用，不是桌宠的运行时提示词。遇到“日志里说成功，用户却没看到”的问题，先写清一句话：**谁从哪里发起，哪个组件负责，用户应在哪里看到什么，哪条证据能证明这一步发生过？** 验证管不了的最后一段，就在交付时明说，不把中间状态改名为成功。

## 开发时怎么用

1. **先区分已约定和待决定的行为。** 若“通知”可能指系统弹窗、桌宠发话或原聊天回执，且答案会改变实现，只确认这一点。若用户已说明“前端编排、插件适配渠道、内核鉴权”，直接遵从，不再发明反向注册或内核特判。路径名、当前平台和某次日志只是样本，不是接口契约。
2. **在出错的那一层复现。** 先写出预期失败和可观察结果，再选 mock。Jaeger 收到一个事件不等于测到了调用耗时：按同一次调用核对 span 的起止和父子关系。类似地，`submittedAt` 只证明已提交；明确失败才走重试，肯定回执才按完成语义移除。涉及回执时同时覆盖延迟回执，避免重投。
3. **测试和产品冲突时，先指出冲突的断言。** 明确的渠道、权限和交付边界优先；旧断言过期就改断言，实现违约就改实现。只有两种行为都说得通、且会改变权限或可见结果时才请用户裁决。不因“测试过了”放弃用户提供的复现，也不为小文案变动强加全链路测试。
4. **交付只报告证据达到的那一步。** 例如：“已在空 `PATH` 下完成真实握手；没有发送模型请求。” 对依赖或配置改动，补一句谁读取它、安装时还是运行时读取、是否需要重启。对未复现的历史故障，保留“用户观察 / 待验证”，不要写成已查明的根因。
