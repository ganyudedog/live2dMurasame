# 实时对话方案（LiveKit 版本）

## 0. 运行前置（必须）

1. 必须单独安装并启动 LiveKit Server（本方案不内置 LiveKit Server）。
2. 必须配置服务端密钥，并与 `api_v3.py` 中的 `LIVEKIT_API_KEY`、`LIVEKIT_API_SECRET` 保持一致。
3. 房间创建与生命周期由后端负责：
- 后端在 `/v3/session/create` 中确定 `room_name` 并签发 token。
- 后端 LiveKit worker 使用同一 `room_name` 进房。
- 前端只负责拿 token 后 connect，不负责创建房间。
4. LiveKit 房间由 LiveKit Server 在首个 participant 加入时自动创建，不由前端手工创建。
5. LiveKit 连接依赖 WebSocket 信令：
- 前端 `livekit-client` 连接 `livekit.ws_url`（例如 `ws://127.0.0.1:7880`）。
- 后端 LiveKit worker 也连接同一个 LiveKit Server 的 WS 信令地址。
- 不需要额外自建一套业务 WebSocket 服务（不需要新增 `/ws` 之类路由）。

推荐本机启动方式（任选其一）：
1. Docker：`docker run --rm -p 7880:7880 -p 7881:7881/udp -e LIVEKIT_KEYS="devkey: secret" livekit/livekit-server --dev`
2. 二进制：下载 `livekit-server` 后执行 `livekit-server --dev --bind 0.0.0.0 --keys "devkey: secret"`

## 1. 目标与边界

### 1.1 目标
1. 实时语音链路统一为 LiveKit：房间连接、媒体传输、实时事件通信。
2. 优先降低工程复杂度：不再自建房间 WebSocket 与手写 WebRTC 信令。
3. 将主要工作量放在前端，后端只做最小必要改造。
4. 采用破坏性升级切换主链路，但保留 HTTP 降级链路（`/v3/tts/speak`、`/v3/tts/cancel` 与 HTTP 音频 fallback）。
5. 当前阶段仅支持“用户输入文本 -> Qwen 回复（displayText/speakText）-> TTS 播放 speakText”链路，不包含 ASR。

### 1.2 边界
1. 仅考虑本机部署（同机进程通信）。
2. LiveKit Server 作为独立基础服务运行，不内嵌在前端或 Python API 进程内。
2. 不考虑公网穿透、TURN、云端多租户与复杂安全域。
3. 不建设业务登录鉴权系统，但 LiveKit 连接仍使用短时 token 作为协议入场票据。
4. v2 旧链路不再作为主业务路径。
5. `GET /v3/model/current` 与 `GET /v3/capabilities` 在 MVP 阶段暂时不做。
6. ASR（麦克风输入与语音转文字）后置到下一阶段。
7. 不做兼容：`tts.speak` 仅接受 Qwen 双文本语义，不保留旧的 text 单字段语义。
8. 房间模型固定为单房间（single-room），不做多房间调度。

---

## 2. 破坏性升级声明

1. 客户端不再连接自定义房间 WebSocket。
2. 客户端不再发送或处理自定义 webrtc.offer / webrtc.answer / webrtc.ice 事件。
3. 原先自定义 session.ping / session.pong 心跳机制下线，由 LiveKit 内建连接与重连机制接管。
4. 模型切换与权重切换能力保留并升级到 v3 接口。
5. 主业务链路切换为 LiveKit（Data Channel + 下行音轨），HTTP tts 接口只保留为降级策略。
6. `tts.speak` 的历史 `text` 单字段语义下线，统一使用 `display_text` 与 `speak_text`。
7. 后端不新增 HTTP 路由，沿用现有 v3 接口面。

---

## 3. 新架构总览

采用双平面模型：

1. 实时平面（LiveKit）
- 房间连接：livekit-client 通过 WebSocket 信令连接 LiveKit Server（`ws_url`）。
- 媒体传输：当前仅下行 TTS 音轨（前端通过 subscribe 播放远端音轨；上行麦克风轨与 ASR 后置）。
- 控制事件：通过 LiveKit Data Channel 发送 tts.speak / tts.cancel / model.switch 等控制消息。

说明：
1. WebSocket 信令由 LiveKit Server 提供，不是业务后端自建 WS 服务。
2. 当前业务后端仍主要提供 HTTP 接口（session/create、model/switch、tts fallback）。

2. 配置平面（HTTP）
- 创建会话并获取 token。
- 模型与权重切换、状态查询。
- 能力查询与健康检查。

3. 文本平面（Qwen）
- 输入：用户文本。
- 输出：`displayText`（UI 展示）与 `speakText`（TTS 输入）。
- 约束：当前阶段 TTS 只消费 `speakText`，不直接消费用户原始输入。

### 3.1 关键原则
1. 前端主导契约：字段、状态机、错误码由前端定义。
2. 会话化与可追踪：所有请求携带 session_id 与 request_id。
3. 可取消：任意阶段可按 request_id 取消。
4. 模型门禁：model_ready 为 true 前，不允许进入 TTS 推理。
5. 幂等：基于 config_version 进行模型配置去重。

---

## 4. 角色分工（前端优先）

### 4.1 前端职责（主）
1. LiveKit Room 生命周期管理（connect / reconnect / disconnect）。
2. Data Channel 协议管理（事件发送、接收、去重、重放保护）。
3. TTS 请求状态机管理（queued / started / streaming / finished / canceled / error）。
4. 中断与插话交互（barge-in）策略与 UI 反馈。
5. 连接态与异常态可视化（connecting / reconnecting / disconnected）。

### 4.2 后端职责（最小）
1. 部署并维护 LiveKit Server 可用性（含密钥配置）。
2. 负责房间命名策略与会话签发（`/v3/session/create`）。
3. 提供本机 token 签发接口。
4. 提供模型与权重切换接口（统一 v3）。
5. 承接 Data Channel 请求并驱动 TTS 引擎输出音轨。
6. 保留 `/v3/tts/speak`、`/v3/tts/cancel` 作为降级链路，不新增其他 HTTP 路由。
7. `model/current` 与 `capabilities` 查询接口后置，MVP 暂不实现。

## 5. v3 接口契约（LiveKit 版）

## 5.1 会话创建

### 5.1.1 创建实时会话
- 方法：POST /v3/session/create

请求示例：

```json
{
  "client": "desktop",
  "version": "0.1.0",
  "capabilities": {
    "livekit": true,
    "audio_downlink": true
  }
}
```

响应示例：

```json
{
  "session_id": "sess_01JXYZ",
  "room_name": "pet_local_room",
  "participant_identity": "desktop_local_user",
  "livekit": {
    "ws_url": "ws://127.0.0.1:7880",
    "token": "<jwt>",
    "expires_in": 600
  },
  "server_time": 1775430000
}
```

说明：
1. 这里的 ws_url 是 LiveKit 信令地址，由 livekit-client 内部使用。
2. 前端不再实现自定义房间 WebSocket 客户端。
3. 房间不由前端创建；后端决定 `room_name`，并由 LiveKit Server 在首个 participant 加入时自动创建。

## 5.2 实时控制事件（LiveKit Data Channel，仅控制消息）

统一事件包结构：

```json
{
  "type": "tts.speak",
  "session_id": "sess_01JXYZ",
  "request_id": "req_01",
  "ts": 1775430000123,
  "payload": {}
}
```

### 5.2.1 客户端发送事件
1. tts.speak
2. tts.cancel
3. model.switch
4. session.ping（可选，仅业务诊断，不承担连接保活）

说明：
1. 当前 `tts.speak` 的文本来源是 Qwen 回复中的 `speakText`，不直接使用用户原始输入。
2. `display_text` 只用于 UI 展示与日志，`speak_text` 才是 TTS 合成输入。

tts.speak 示例：

```json
{
  "type": "tts.speak",
  "session_id": "sess_01JXYZ",
  "request_id": "req_01",
  "ts": 1775430000123,
  "payload": {
    "display_text": "你好，今天过得怎么样？",
    "speak_text": "你好，今天过得怎么样？",
    "text_lang": "zh",
    "prompt_lang": "zh",
    "ref_audio_path": "C:/voices/ref.wav",
    "prompt_text": "示例参考文本",
    "text_split_method": "cut5",
    "speed_factor": 1.0,
    "fragment_interval": 0.2,
    "top_k": 5,
    "top_p": 1.0,
    "temperature": 1.0,
    "streaming_mode": true,
    "media_type": "ogg"
  }
}
```

tts.cancel 示例：

```json
{
  "type": "tts.cancel",
  "session_id": "sess_01JXYZ",
  "request_id": "req_01",
  "ts": 1775430000456,
  "payload": {
    "reason": "barge_in"
  }
}
```

### 5.2.2 服务端返回事件
1. session.ready
2. tts.queued
3. tts.started
4. tts.chunk_meta
5. tts.finished
6. tts.canceled
7. tts.error
8. model.switching
9. model.switched
10. model.switch_failed
11. model.unchanged

示例：tts.started

```json
{
  "type": "tts.started",
  "session_id": "sess_01JXYZ",
  "request_id": "req_01",
  "ts": 1775430000789,
  "payload": {
    "trace_id": "trace_abc",
    "queue_ms": 3
  }
}
```

## 5.3 模型与权重管理

### 5.3.1 切换模型与权重
- 方法：POST /v3/model/switch

请求示例：

```json
{
  "session_id": "sess_01JXYZ",
  "request_id": "req_model_01",
  "payload": {
    "reason": "startup",
    "config_version": "modelcfg_20260406_120001",
    "model_id": "murasame_v1",
    "gpt_weights_path": "D:/models/gpt/murasame.ckpt",
    "sovits_weights_path": "D:/models/sovits/murasame.pth",
    "ref_audio_path": "D:/refs/murasame_ref.wav",
    "prompt_text": "示例参考文本",
    "prompt_lang": "zh"
  }
}
```

响应示例：

```json
{
  "ok": true,
  "request_id": "req_model_01",
  "state": "switching",
  "model_ready": false
}
```

补充约定：
1. reason 允许值：startup | model_switch | settings_update。
2. config_version 由前端生成。
3. 前端按 config_version 去重，无改动不重复调用。
4. 后端可返回 model.unchanged 作为幂等反馈。

### 5.3.2 查询当前模型（暂时不做）
- 状态：MVP 后置，不进入首轮实现范围。
- 预留方法：GET /v3/model/current?session_id=...
- 用途：用于调试与重启后状态对齐，首轮由前端本地状态与切换事件维护。

## 5.4 能力查询（暂时不做）
- 状态：MVP 后置，不进入首轮实现范围。
- 预留方法：GET /v3/capabilities
- 用途：用于多后端能力协商；当前单机场景先不需要。

## 6. 启动与切模链路（前置权重同步）

1. 应用启动时读取模型配置。
2. 若 gpt_weights_path 与 sovits_weights_path 均存在，先调用一次 /v3/model/switch。
3. 当 model_ready = true 后，再调用 /v3/session/create 并连接 LiveKit 房间。
4. 模型配置为空时，不等待文字 AI，待用户补齐配置后再触发切换。
5. 切模成功后若 config_version 未变化，不重复切换。
6. 若 LiveKit 连接失败或中途不可用，自动降级到 HTTP speak/cancel + HTTP 音频播放。

## 7. 状态机（LiveKit 版）

## 7.1 连接状态
1. idle
2. connecting
3. connected
4. reconnecting
5. disconnected

## 7.2 模型状态
1. unconfigured
2. switching
3. ready
4. failed

## 7.3 TTS 请求状态
1. queued
2. synthesizing
3. streaming
4. finished
5. canceled
6. error

状态约束：
1. canceled 与 finished 互斥。
2. 任意中间态允许转移到 error。
3. tts.cancel 到达后，后续晚到分片必须丢弃。
4. model_ready = true 前，TTS 不得进入 synthesizing。

---

## 8. 错误模型

统一错误结构：

```json
{
  "ok": false,
  "error": {
    "code": "TTS_INVALID_PARAM",
    "message": "text_lang is required",
    "request_id": "req_01",
    "retryable": false,
    "phase": "validate"
  }
}
```

建议错误码：
1. SESSION_CREATE_FAILED
2. LIVEKIT_CONNECT_FAILED
3. INVALID_EVENT_TYPE
4. TTS_INVALID_PARAM
5. TTS_ENGINE_BUSY
6. TTS_ENGINE_ERROR
7. REQUEST_CANCELED
8. MODEL_SWITCH_FAILED
9. WEIGHTS_NOT_FOUND
10. MODEL_NOT_READY

## 9. 实施清单（前端 80% / 后端 20%）

说明：
1. 不新增后端 HTTP 路由。
2. 主链路使用 LiveKit；HTTP speak/cancel 与 HTTP 音频保留为降级策略。
3. 统一单房间模型。

### 阶段 A：契约冻结（0.5 天）

前端：
1. 冻结 Data Channel 事件 schema（`tts.speak`、`tts.cancel`、`tts.started`、`tts.finished`、`tts.error`、`model.switched` 等）。
2. 冻结前端状态机（连接态、模型态、请求态）。
3. 冻结降级判定条件（连接失败、连接中断、事件超时）。

后端：
1. 确认沿用现有接口：`/v3/session/create`、`/v3/model/switch`、`/v3/tts/speak`、`/v3/tts/cancel`、`/v3/health`。
2. 确认不新增其他 HTTP 接口。

验收：
1. 产出最终契约文档与状态机图。

### 阶段 B：前端主链路接入（1-2 天）

前端：
1. 接入 `livekit-client` 建立房间连接（single-room）。
2. 建立 Data Channel 收发层，统一 request_id 追踪。
3. 将 TTS 主请求由 HTTP speak 切到 Data Channel `tts.speak`。
4. 将 cancel 主请求由 HTTP cancel 切到 Data Channel `tts.cancel`。
5. 通过 subscribe 接入下行远端音轨播放器，替代主链路的 HTTP 音频响应播放。
6. 保留并可切换到 HTTP fallback（请求与播放双降级）。

后端：
1. 无新增 HTTP 路由要求。

验收：
1. 前端可通过 LiveKit 发起 speak/cancel，并完成播放与中断。
2. LiveKit 断开时可自动回落到 HTTP speak/cancel 与 HTTP 音频播放。

### 阶段 C：后端内部桥接（0.5-1 天）

前端：
1. 与后端联调 Data Channel 事件字段与时序。

后端：
1. 新增 LiveKit 内部 worker（或协程）加入房间并处理 Data Channel 指令。
2. 将 `tts.speak` Data Channel 指令映射到现有 TTS 推理逻辑。
3. 将 `tts.cancel` Data Channel 指令映射到现有取消标记逻辑。
4. 推理音频通过 LiveKit 下行音轨发布。
5. 保留 `/v3/tts/speak` 与 `/v3/tts/cancel` 作为降级路径。

验收：
1. 后端在不增加 HTTP 路由前提下，支持 Data Channel speak/cancel。
2. LiveKit 与 HTTP 两条链路都可独立跑通。

### 阶段 D：模型切换联动与自动预热（0.5 天）

前端：
1. Electron 启动后自动读取配置并触发一次 `model/switch`。
2. TTS 设置变更时，要求 GPT 与 SoVITS 权重都有效才触发切换。
3. 模型切换后自动再触发一次预热。
4. 前端保持 `config_version` 幂等，避免重复切换。

后端：
1. 继续复用现有 `model/switch` 门禁，不新增接口。

验收：
1. 首句不再承担主要切模时延。
2. 模型变更链路日志可按 request_id 对齐。

### 阶段 E：稳定性与延迟优化（0.5-1 天）

前端：
1. 统计 `queue_ms`、`ttfa_ms`、`cancel_ms`、`fallback_count`。
2. 增加连接恢复与去重策略，避免重复播报。

后端：
1. 输出关键阶段 trace（排队、开始、首包、结束、取消）。
2. 优化取消即时性与首段响应。

验收：
1. 能给出一版可复现的延迟与稳定性报告。

### 阶段 F：ASR（下一阶段）

前端：
1. 上行麦克风轨采集与传输，和asr解析。

后端：
1. 无

验收：
1. 全双工语音链路可演示。

## 10. MVP 验收标准

1. 功能
- 前端可通过 livekit-client 连接本地房间。
- 可发送 tts.speak 并收到下行音轨播放。
- 可按 request_id 取消并得到 canceled 或 finished 终态。
- 可完成模型与权重切换，且支持 config_version 幂等。
- 模型未就绪时，TTS 请求不可进入推理。
- 主链路为 LiveKit，且在连接失败时可自动降级到 HTTP speak/cancel 与 HTTP 音频 fallback。
- 当前仅支持文本输入触发语音回复，不包含 ASR。
- Qwen 的 `displayText` 与 `speakText` 分流正确：UI 使用 displayText，TTS 仅使用 speakText。

2. 协议一致性
- 后端严格按前端契约实现，不新增未约定语义字段。

3. 性能
- 有可观测的首包时长和取消时长。

---

## 11. 执行建议

1. 先完成前端主链路接入（Data Channel + 音轨播放），再做后端内部桥接联调。
2. 后端仅做内部能力改造，不扩大 HTTP 接口面。
3. speak/cancel 与 HTTP 音频 fallback 全程保留，作为稳定性兜底。
4. 统一单房间模型，减少调度复杂度与故障面。
5. ASR 作为下一阶段独立推进，不与当前 MVP 绑定。
